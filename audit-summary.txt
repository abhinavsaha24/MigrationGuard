# MigrationGuard Benchmark: Ground Truth Methodology\n## Overview\nGround truth in the MigrationGuard benchmark must be established entirely independently from the outputs of either the MigrationGuard system or the Atlas baseline. Using the output of a system to evaluate the system itself would create circular logic and invalidate the research findings.\n## Ground Truth Establishment\n### 1. Controlled Fixtures (Track B)\nFor synthetic injected faults, ground truth is mathematically guaranteed by the injection mechanism.\n- **Method**: We take a known, stable schema version `V1` and apply a single specific mutation (`M`). We analyze the resulting database schema `V2`.\n- **Labeling Rules**:\n- If `M` explicitly drops a column that was active in `V1`, the ground truth is **UNSAFE (COLUMN_REMOVAL)**.\n- If `M` drops a column `A` and creates a column `B` with the same type, the ground truth is **UNSAFE (DESTRUCTIVE_RENAME)**.

docs\decisions\M2-M4-AUDIT.md
--- TITLE: # M2–M4 Engineering Audit ---
# M2–M4 Engineering Audit\n## Summary\nThis audit inspects the MigrationGuard M0/M1 implementation to identify weaknesses, hardcoded values, and architectural limitations before refactoring into the generic M2–M4 components. The review focuses on modularity, error handling, lifecycle management (Docker/Node processes), and platform-specific behaviour (Windows).\n## Critical Findings\n- **Finding:** Windows process leakage in `application-runner`.\n- **Severity:** CRITICAL\n- **Affected module:** `packages/application-runner`\n- **Reason:** Node's `childProcess.kill('SIGKILL')` on Windows does not terminate process trees properly. # M6 Audit Log: Compatibility Matrix\n## 1. Summary\nPrior to M6, the `cli` orchestrator implemented a hardcoded procedural script that selectively tested 3 of the 4 rolling deployment states (omitting `NEW APP + V1 DB`). M6 generalized this into a reusable `CompatibilityMatrixEngine`.\n## 2. Findings & Design Decisions\n### 2.1 Decoupling Execution from Analysis\n- **Decision**: The Matrix Engine must not know about `users.name` or `DESTRUCTIVE_RENAME`.\n- **Rationale**: An orchestrator should only coordinate lifecycles (start DB, start app, fire workload). Hardcoding Prisma exception strings inside the Engine would violate single responsibility. We instead emit a `WORKLOAD_FAILURE` and let the downstream `CompatibilityAnalyzer` inspect the JSON bodies for Prisma errors.\n### 2.2 Execution Ordering\n- **Decision**: The execution occurs in a strict V1 setup -> (OLD, NEW) -> V2 setup -> (OLD, NEW) sequence.\n- **Rationale**: Re-creating the Docker sandbox for each quadrant is excessively slow. By moving the database forward in time (`V1` -> `V2`), we can test the `OLD` and `NEW` applications simultaneously against the current database epoch before advancing it, reducing E2E verification time significantly.
