# Architecture Decision Records (ADRs)

This directory documents the core architectural decisions governing MigrationGuard.

---

## ADR-001: Why Four-State Matrix Verification?

- **Status**: Accepted (Frozen Architecture)
- **Context**: Static migration linters (e.g. Atlas, Prisma validate) inspect migration DDL in isolation. However, zero-downtime rolling deployments involve a mixed-version window where old application pods run concurrently against the newly migrated database, or new application pods boot before the database migration finishes.
- **Decision**: MigrationGuard evaluates all four permutations of application versions (`OLD`, `NEW`) and database schema states (`V1`, `V2`):
  1. `Cell 1 (OLD APP + V1 DB)`: Pre-deployment baseline.
  2. `Cell 2 (NEW APP + V1 DB)`: Forward compatibility.
  3. `Cell 3 (OLD APP + V2 DB)`: Backward compatibility (critical zero-downtime invariant).
  4. `Cell 4 (NEW APP + V2 DB)`: Steady post-deployment state.
- **Consequences**: Conclusively captures runtime failures (such as `DESTRUCTIVE_RENAME` or `NOT_NULL_ADDITION`) that static analyzers miss or flag with false positives.

## ADR-002: Why Deterministic Verdict?

- **Status**: Accepted
- **Context**: LLMs are probabilistic and prone to hallucination, non-reproducibility, and sycophancy.
- **Decision**: Pass/Fail verdicts are strictly computed by the deterministic matrix engine based on actual HTTP responses, SQL errors, and database constraint feedback. AI is never in the detection loop and cannot decide or alter verdicts.
- **Consequences**: Scientific reproducibility, zero hallucinated verdicts, auditable compliance.

---

## ADR-003: Why AI is an Optional Assistance Layer?

- **Status**: Accepted
- **Context**: Many enterprise and air-gapped environments forbid external LLM API calls or enforce strict data privacy boundaries.
- **Decision**: MigrationGuard functions completely with `AI_ENABLED=false`. When enabled, the AI layer only reads observed evidence and documentation to explain errors and translate proposals into natural language.
- **Consequences**: The core verifier has zero hard runtime dependency on Gemini or any third-party AI provider.

---

## ADR-004: Why No Vector Database?

- **Status**: Accepted
- **Context**: Complex RAG stacks with vector embeddings introduce index drift, latency, external dependencies, and operational overhead for documentation that fits into memory or indexed relational storage.
- **Decision**: MigrationGuard uses PostgreSQL full-text search (FTS) and curated in-memory topic indexing for documentation retrieval rather than an external vector database.
- **Consequences**: Eliminates Chroma/Pinecone/Milvus infrastructure; sub-millisecond retrieval with zero external service dependencies.

---

## ADR-005: Why Deterministic Repair Planner?

- **Status**: Accepted
- **Context**: LLM-generated code and migrations frequently introduce subtle syntax errors, security regressions, or irreversible schema loss.
- **Decision**: Repair proposals are generated by deterministic strategy planners (`Expand/Contract`, `Nullable With Backfill`) which mathematically calculate required schema alterations, multi-phase migration steps, and schema diffs from ASTs and schema hashes.
- **Consequences**: 100% reproducible proposals, verifiable diffs, zero hallucinated DDL.

---

## ADR-006: Why Explicit Human Approval Boundary?

- **Status**: Accepted
- **Context**: Automated tools that mutate production schemas or execute arbitrary SQL pose catastrophic data loss risks.
- **Decision**: Verification, proposal generation, and AI explanations are strictly read-only. Modification of project files or schemas requires explicit user authority (`migrationguard repair --approve <id>` or interactive confirmation). `--yes` only approves an already validated, deterministic proposal.
- **Consequences**: Prevents accidental data destruction and maintains strict human-in-the-loop governance.

---

## ADR-007: Why PostgreSQL Full-Text Search (FTS)?

- **Status**: Accepted
- **Context**: Fast, reliable search across schema objects, evidence logs, and verification runs is needed without adding Elasticsearch or Opensearch.
- **Decision**: Use native PostgreSQL FTS (`tsvector` / `tsquery`) and GIN indexes.
- **Consequences**: Minimal operational footprint, transaction-safe indexing, zero additional cloud components.

---

## ADR-008: Why CLI is the Execution Boundary?

- **Status**: Accepted
- **Context**: Docker execution and local filesystem isolation require clear security boundaries.
- **Decision**: The CLI executes sandboxes, runs application processes, and coordinates verification locally in the developer's environment or CI runner. The web backend does not possess Docker socket permissions or arbitrary shell execution capabilities.
- **Consequences**: Hardened security posture; web backend remains an isolated API and persistence layer.

---

## ADR-009: Why Cloudflare Tunnel?

- **Status**: Accepted
- **Context**: Exposing backend ports directly to the public internet creates firewall vulnerabilities and requires complex certificate rotation.
- **Decision**: Public traffic routes via Cloudflare Tunnel directly to the reverse proxy ingress (`127.0.0.1:8080`), keeping all application, database, and storage ports completely closed to external ingress.
- **Consequences**: Zero open public ports on origin server; automated DDoS protection; authenticated ingress.

---

## ADR-010: Why S3-Compatible Evidence Storage?

- **Status**: Accepted
- **Context**: Verification runs produce rich JSON evidence records, execution logs, and database traces that should not bloat relational database tables.
- **Decision**: Store raw evidence artifacts in S3-compatible object storage (MinIO for local/on-prem, AWS S3 for cloud), with SHA-256 integrity content digests stored in PostgreSQL.
- **Consequences**: Infinite horizontal scalability for evidence retention, immutable content-addressable storage, and fast database transactions.
