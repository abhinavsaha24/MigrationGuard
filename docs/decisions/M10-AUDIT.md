# MigrationGuard M10 Audit Report

## Phase 0 - Architectural Boundaries Audit

### 1. Existing Verification Engine (M0-M9)

The `MigrationGuard` monorepo currently contains a highly modular and robust CLI-driven verification engine.

- **Domain Separation:** Clean separation of concerns between `sandbox`, `migration-engine`, `application-runner`, `workload`, `matrix-engine`, `compatibility`, `evidence`, and `benchmark-runner`.
- **Infrastructure Footprint:** Relies on ephemeral Docker containers (`PostgresSandbox`) for local PostgreSQL instances.
- **Reporting:** Uses the `@migrationguard/evidence` package to produce standardized JSON and Markdown reports containing execution matrices and fault classifications.
- **Current CLI (`@migrationguard/cli`):** Thin orchestrator built on Commander that invokes the matrix engine.

### 2. Dependency Assessment

- `package-lock.json` and workspaces are strictly managed.
- Node.js 20 environment is enforced through `.github/workflows/migrationguard.yml`.
- There are no extraneous database servers currently deployed. The system assumes a stateless runtime where tests create and destroy DBs on the fly.

### 3. Backend Architecture Gap (The M10 Goal)

Currently, all verification runs and evidence reports are stored as local files (`reports/MG-VERIFY-xxx.json`). There is no historical persistence, no way to aggregate runs across different developers, and no way to review or manage migration safety manually.

The M10 requirements demand a persistent **Hosted Backend** with:

1. **Authentication & Authorization:** Role-based access (ADMIN, REVIEWER) with secure session handling.
2. **Persistent Database:** A centralized PostgreSQL instance (distinct from the ephemeral sandbox databases) to store Run Records, Compatibility Matrices, Evidence, and User metadata.
3. **Object Storage (S3):** For storing immutable presentation versions, generated PDF reports, and associated binaries without bloating the relational DB.
4. **Publishing Workflow:** Immutably versioning presentation files and providing access controls.

### 4. Technical Constraints

- The backend API must **NOT** duplicate the verification execution logic (i.e., it should not run Docker or start legacy applications directly). It will serve purely as a storage, presentation, and management layer for the verification outputs generated by the CLI/CI pipeline.
- It will be implemented as a separate workspace package: `apps/server` using Fastify and Prisma.

## Conclusion

The existing M0-M9 architecture is stable, regression-protected, and well-suited to operate completely decoupled from the new M10 backend. The CLI can optionally push results to the new REST API. The M10 backend will focus strictly on persistence, security, authentication, and object storage.
